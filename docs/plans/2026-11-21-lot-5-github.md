# Lot 5 : GitHub (source « issues GitHub », livraison « PR GitHub »)

Plan allégé, v1 macOS seul. Dépend du lot 4. Lecture faite : `sources/tasks-dir.js`, `deliveries/local-merge.js`, `deliveries/index.js`, `core/tasks.js` (`readSource`, `deliverTask`), `core/run-file.js`, `core/config.js`.

## 1. But et périmètre

But : une mission prend deux issues d'un dépôt d'essai, ouvre deux PR relues, les fusionne sur la branche d'intégration et ferme les issues.

Dans la v1 :
- source `github-issues` : les issues ouvertes portant un libellé (défaut `relaylead`) deviennent des tâches `issue-<n>` ;
- livraison `github-pr` : branche et worktree par tâche (comme `local-merge`), push, `gh pr create` vers la branche d'intégration, contrôle de relecture, `gh pr merge`, fermeture de l'issue ;
- tous les appels `gh` et `git` passent par `runFileSync` (`core/run-file.js`), tableau d'arguments, jamais de shell ;
- config : `source: { type: 'github-issues', repo?: 'owner/name', label: 'relaylead' }`, `delivery: { type: 'github-pr', branch: 'relaylead/integration', runHooks: true, remote: 'origin' }`. `repo` absent : `gh` le déduit du dépôt courant.

Hors v1 : GitHub Enterprise, plusieurs dépôts, dépendances entre issues (aucune : `depends: []`), mise à jour des issues par commentaires de progression, webhooks, forks, relecture humaine attendue en boucle (la relecture est celle du lead, voir tâche 3), Windows/Linux réels (le faux `gh` tourne en CI, essai réel macOS seulement).

## 2. Tâches

### Tâche 1 : l'appel à `gh` (`core/github.js`, nouveau)
- `gh(args, { cwd })` : `runFileSync('gh', args, { cwd, encoding: 'utf8', timeout: gitTimeoutMs(), windowsHide: true, env: { ...process.env, GH_PROMPT_DISABLED: '1', NO_COLOR: '1' } })`. Retourne stdout sans espaces de bord.
- `ghJson(args, opts)` : idem avec `JSON.parse`.
- Échecs en `codedError` : `gh-missing` (ENOENT), `gh-not-authenticated` (sortie contenant `gh auth login`), `gh-failed` ({ args, detail }). Textes en anglais et en français dans `core/messages.js`.
- `checkGh()` : `gh auth status`, appelé par `prepareMission` et utilisable par `doctor` (lot 4) plus tard sans le toucher.
- Tests (`test/github.test.js`) : faux `gh` écrit par `fixtures/fake-gh.js` (voir tâche 5) mis en tête du `PATH` du test ; ENOENT donne `gh-missing` ; statut 1 donne `gh-failed` avec le détail.

### Tâche 2 : la source (`sources/github-issues.js`, nouveau) et son branchement
- `list(source)` : `gh issue list --state all --label <label> --limit 100 --json number,title,body,state` (+ `--repo` si `repo`). Chaque issue donne `{ id: 'issue-<n>', file: null, title, state: 'todo' | 'done' (CLOSED), depends: [], ask: null, body }`. Même forme que `tasks-dir.list` : rien d'autre ne change dans `core/tasks.js` hors le branchement.
- `markDone(source, id)` : `gh issue close <n> --comment "Delivered by relaylead"` ; refermer une issue déjà fermée n'est pas une erreur (la livraison peut être rejouée).
- `core/tasks.js` `readSource` : dispatch sur `source.type` (`tasks-dir` | `github-issues`) au lieu du `throw`. `checkDependencies` n'est appelé qu'avec `tasks-dir` ou tolère `depends: []` (il le tolère déjà).
- Tests (`test/github-issues.test.js`) : liste de 3 issues dont une fermée donne 2 `todo` et 1 `done`, ids `issue-1`… ; libellé et `--repo` bien passés au faux `gh` (journal d'appels) ; `markDone` deux fois ne lève pas.

### Tâche 3 : la livraison (`deliveries/github-pr.js`, nouveau ; `deliveries/index.js`)
Réutilise `local-merge` plutôt que de le copier : y exporter (sans changer leur code) `integrationDir`, `taskBranch`, `git`, `checkDone`, `removeWorktree`, `branchExists`, `prepareTask`, `prepareMission`, `cleanMission`, `removeMission`, `missionBranches`, `missionWorktrees`. `github-pr` les reprend tels quels et ajoute :
- `prepareMission(mission)` : `checkGh()`, `local-merge.prepareMission`, puis `git push <remote> <branche d'intégration>` (la PR a besoin de la base sur le dépôt distant).
- `deliver(mission, task, { runHooks })` : (1) `checkDone` ; (2) `git push --force-with-lease <remote> <task branch>` ; (3) PR : `gh pr list --head <branche> --state open --json number` ; absente, `gh pr create --base <branche d'intégration> --head <branche> --title <titre> --body "Closes #<n>\n\n<résumé du résultat>"`, le numéro se relit par `gh pr view <branche> --json number` ; (4) relecture : `gh pr view <n> --json reviewDecision,state` ; `CHANGES_REQUESTED` refuse (`pr-changes-requested`), la tâche reste `done` pour une correction ; sinon le lead a relu (méthode du lead, voir ci-dessous) ; (5) `gh pr merge <n> --merge` (pas de `--delete-branch` : la branche locale est nettoyée par `finish`) ; conflit signalé par `gh` : `pr-merge-conflict` ; (6) `git fetch <remote>` puis `git merge --ff-only <remote>/<branche d'intégration>` dans le worktree d'intégration (la branche locale suit le distant) ; (7) `sources/github-issues.markDone` ; (8) `finish`.
- `finish` : supprime worktree et branche de la tâche (reprend celle de `local-merge`, sans la ligne d'état qui n'existe pas ici). Rejouable : PR déjà fusionnée (`state: MERGED`) saute les étapes 2 à 5.
- La relecture « relue » du critère : le lead fait relire la PR (consigne de la méthode `code`, déjà en place pour `local-merge`) et poste son avis par `gh pr review <n> --approve` ou `--request-changes -b <texte>` ; les contrôles de `deliver` l'exigent seulement par l'absence de `CHANGES_REQUESTED`. Un auteur ne peut pas approuver sa propre PR sur le vrai GitHub : le compte du dépôt d'essai est donc le même, et l'approbation n'est pas exigée, seulement le refus respecté. Ajouter une ligne dans `catalog/` (consigne du lead) disant de poster l'avis avec `gh pr review` quand la livraison est `github-pr`.
- `deliveries/index.js` : `if (type === 'github-pr') return githubPr;` et le message d'erreur liste les trois types.
- Codes d'erreur nouveaux (anglais et français) : `pr-changes-requested`, `pr-merge-conflict`, `push-failed`.
- Tests (`test/github-pr.test.js`, dépôt git temporaire avec un dépôt « distant » nu `file://`, faux `gh`) : `deliver` pousse, crée la PR avec la bonne base, la fusionne, ferme l'issue, la branche d'intégration locale contient le commit ; rejouer `deliver` après un échec entre fusion et fermeture ne recrée pas de PR et ferme l'issue ; `CHANGES_REQUESTED` refuse sans fusionner ; conflit de fusion refuse avec `pr-merge-conflict`.

### Tâche 5 : le faux `gh` et le scénario de bout en bout
- `fixtures/fake-gh.js` (+ lanceur `fixtures/bin/gh` exécutable, et `gh.cmd` non nécessaire en v1 macOS) : état dans un JSON (`FAKE_GH_STATE`), journal d'appels. Gère `auth status`, `issue list|close`, `pr list|create|view|review|merge`. `pr merge` fusionne réellement dans le dépôt « distant » nu de la fixture (`git` sur le clone de travail du faux) pour que le test vérifie le contenu. Variables pour forcer `CHANGES_REQUESTED` et un échec.
- `test/e2e/github-mission.test.js` : dépôt d'essai local avec distant nu, deux issues (libellé `relaylead`), faux `gh` sur le `PATH`, mission lancée avec le faux agent (`fixtures/missions.js` pour les rapports). Le faux agent écrit un commit par tâche. Vérifie : deux PR créées (base = branche d'intégration), deux fusions, les deux issues `CLOSED`, la branche d'intégration du distant contient les deux commits, les worktrees de tâche sont supprimés, `relaylead task list` dit `delivered` pour les deux.
- Aucun appel au vrai GitHub : le test échoue s'il trouve un vrai `gh` avant le faux (le `PATH` du test ne contient que `fixtures/bin`, `process.execPath` et git).
