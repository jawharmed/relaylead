## 1. But et périmètre

**But** : une session d'équipe ne bloque jamais sur une demande d'autorisation, mais l'humain est prévenu et décide. Les actions hors liste blanche et les actions irréversibles deviennent des questions (`relaylead answer` existe déjà) ; la mission continue sur le reste.

**Dans la v1**
- Liste blanche (existe : `guard.allow` + outils du profil, `core/hooks/permission.js`) : une demande hors liste est refusée avec message **et** pose une question `perm-<hash>` ; une réponse « autoriser » rend l'action permise ensuite.
- Autorisation à usage unique pour l'irréversible (`PreToolUse`) : question `irr-<hash>`, réponse valable une seule fois pour cette commande exacte.
- Garde-fous de base : liste d'irréversibles (suppression récursive hors dossier de mission, `git reset --hard`, `git clean -f`, `git branch -D`, `git push --delete`, `git checkout -- .`/`git restore .`, `git stash drop|clear`) en plus de l'existant (secrets, branche protégée, push forcé, dossier d'état). Issue #60.
- Notification macOS (canal `system`, `osascript`), envoyée à chaque nouvelle question et en rappel.
- Réglage `questions.onTimeout` : `wait` (défaut, existe) | `recommended` | `skip`, avec `questions.timeoutMinutes` (défaut 60).

**Hors v1** (reporté) : `web-reader` en quarantaine, canaux `agent`, `ntfy`, `command`, liste `alerts`, résumé quotidien, vérification du mode sans autorisations natif, jetons de travaux lourds, interdits du projet au-delà de `guard`, test de notification à l'installation (lot 4).

## 2. Tâches

### T1. Issue #60 : glob de Grep à plusieurs motifs (`core/guard.js`, `test/guard.test.js`)
Dans `checkToolUse`, le `glob` de `Grep` est découpé sur les espaces (et virgules) avant jugement ; chaque morceau passe par `checkFileWord(piece, searched, guard, stateDir, true)`. Un seul morceau suspect refuse. On ne vérifie pas le comportement réel de Claude Code : on juge plus large, ce qui est sans risque. Ajouter aussi : un `Grep` **sans `glob`** dont `path` est un parent du dossier d'état (ou le dossier d'état lui-même) est refusé avec la raison `access to the mission state folder`, sauf si `path` est dans un worktree de la mission (ne pas bloquer les recherches normales ; `path` absent = cwd, jugé comme aujourd'hui). Mettre à jour le commentaire « Known gap » de `checkToolUse`.
Tests : `glob: "*.js .env"` refusé ; `glob: "*.js *.ts"` autorisé ; `glob: "*.js,.env"` refusé ; Grep sans glob sur le parent du dossier d'état refusé, sur un sous-dossier de travail autorisé.

### T2. Irréversible et garde-fous de base (`core/guard.js`, `core/hooks/pretool.js`, `core/questions.js`)
- `core/guard.js` : fonction `irreversibleReason(piece, dir, stateDir)` appelée depuis `checkPiece` ; renvoie la raison (`irreversible: git reset --hard`) ou null. Les refus **absolus** existants (secrets, branche protégée, push forcé, dossier d'état) restent des `deny` sans question. Résultat de `checkToolUse` : `{decision: 'deny', reason, irreversible: true}` pour les irréversibles.
- Identifiant d'autorisation : `actionHash(tool_name, texte normalisé)` = 12 premiers hex de sha256 de `tool_name + '\0' + commande` (mots joints par un espace unique). Réutilisé par T3.
- `pretool.js` : sur un refus `irreversible`, (a) si `questions/irr-<hash>.answer.json` existe avec `choice` = « Allow once » et que `questions/irr-<hash>.used.json` n'existe pas, écrire `.used.json` (par `writeJsonExclusive`, fichier dont le **hook** est seul rédacteur) et laisser passer ; (b) sinon refuser avec le message « Asked the user (question irr-<hash>), continue with the rest » et créer la question par `askQuestion` : `key: 'irr-<hash>'`, texte = la commande, options `["Allow once", "Refuse"]`, `recommended: 2`, plus un champ `kind: 'irreversible'` accepté par `askQuestion` (champ optionnel, `null` sinon). Après usage ou après « Refuse », une nouvelle tentative est refusée sans nouvelle question (la clé existe : `askQuestion` rend l'existante).
- La session de l'équipier ne voit pas la réponse : le lead (ou l'humain) relance la tâche (`task retry` existe). Ajouter une phrase dans `catalog/profiles/lead.md` : une question `irr-*` ou `perm-*` répondue « Allow… » → `relaylead task retry <id>` si la tâche a échoué pour ce motif.
Tests : commande `git reset --hard` refusée et question créée ; après réponse « Allow once », première exécution permise, deuxième refusée ; `Refuse` reste refusé ; un `push --force` reste refusé sans question ; ne pas lever d'exception hook (sortie 0).

## 3. Critère « terminé » (faux agent, `npm test` sur macOS)
1. Une mission rencontre une commande hors liste et une action irréversible : deux questions ouvertes, deux notifications (binaire injecté), la tâche indépendante est livrée, la mission n'est pas bloquée.
2. Réponse « Allow once » : l'action passe une fois puis est refusée ; « Always allow » : passe toujours ; « Refuse » : jamais.
3. `questions.onTimeout: recommended` applique l'option recommandée d'une question ordinaire après le délai, jamais celle d'une autorisation ni d'un irréversible ; `wait` ne fait que rappeler.
4. Issue #60 : `Grep` avec `glob: "*.js .env"` est refusé ; recherche normale autorisée. Fermer l'issue par la PR (`Closes #60`).
5. `npm test` vert, aucune écriture hors `RELAYLEAD_HOME` de test ; essai à la main avec Claude sur macOS : une vraie notification s'affiche (à confirmer par l'auteur).
